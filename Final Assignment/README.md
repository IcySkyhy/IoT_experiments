# 智慧丁字路口协同交通灯控制系统

## 一、项目概述

基于 3 台 RDK X5 构建一个 **丁字路口** 交通灯智能协同系统。每台 RDK 负责一个方向的来车检测与交通灯控制，通过有线网络和 MQTT 消息协议实现三方实时协商，动态调整信号灯配时，并具备救护车识别优先通行和设备掉线安全降级能力。

```
             ║ ↓ B左转 ║ ↓ B右转 ║
             ║  车道4  ║  车道3  ║
        ═════╬════════╬════════╬═════════════
  A直行 → 车道1                    车道6 ← C左转
        ─────                    ─────────────
  A左转 → 车道2                    车道5 ← C右转
        ═════╬════════╬════════╬═════════════
             ║        ║        ║
             ║  (无路) ║  (无路) ║
```

### 路口拓扑

丁字路口（T-intersection），三个方向分别为 **A（西）**、**B（北）**、**C（东）**，南侧无路。

| 方向 | RDK  | 车道 1       | 车道 2       |
| ---- | ---- | ------------ | ------------ |
| A 西 | pi1  | 直行（→东）  | 左转（→北）  |
| B 北 | pi2  | 左转（→西）  | 右转（→东）  |
| C 东 | pi3  | 直行（→西）  | 右转（→北）  |

> 注：丁字路口南侧不通，因此不存在"右转→南"或"左转→南"的转向。

## 二、硬件方案

### 每台 RDK 配置

| 组件 | 型号 / 规格 | 接口 | 用途 |
| ---- | ----------- | ---- | ---- |
| 摄像头 | USB 摄像头 / MIPI CSI | USB / MIPI | 监测本方向两车道来车数量、识别救护车 |
| LED 矩阵 | WS2812 8×4（32 颗） | SPI Bus 1 | 交通灯显示（左右各 4×4 对应两条车道） |
| RDK X5 | Ubuntu 22.04 AArch64 | — | 主控、图像处理、通讯 |

### LED 矩阵布局（8×4）

```
 ┌──── 车道1 灯 ────┬──── 车道2 灯 ────┐
 │  ● ● ● ●        │        ● ● ● ●  │
 │  ● ● ● ●        │        ● ● ● ●  │
 │  ● ● ● ●        │        ● ● ● ●  │
 │  ● ● ● ●        │        ● ● ● ●  │
 └──────────────────┴──────────────────┘
```

每个 4×4 区域可以：
- **纯色块模式**：全绿 / 全红 / 全黄，直观显示通行状态
- **图标模式**：在 4×4 像素内绘制 ↑（直行）、←（左转）、→（右转）箭头图案，标识车道类型

## 三、软件方案

### 3.1 车辆检测与计数

每台 RDK 使用摄像头拍摄本方向的两条车道，通过图像识别进行：

1. **车辆计数**：检测画面中车辆数量。本实验中使用**预制图片**代替实际车辆——将普通车辆图片和救护车图片摆放在摄像头前方模拟来车。
2. **救护车识别**：识别画面中是否存在救护车（以颜色/形状/标志特征区分）。

> 实现方式可选：
> - **传统 CV**：OpenCV 颜色阈值 + 轮廓检测，识别红蓝色特征的救护车
> - **轻量模型**：YOLOv5-nano / MobileNet-SSD 等轻量目标检测模型，在 RDK X5 上可实现实时推理

### 3.2 信号灯调度算法

采用**基于流量的自适应配时**策略：

```
核心逻辑：
1. 每个周期（如 60 秒）分为若干相位
2. 各方向将车辆计数通过 MQTT 上报至所有节点
3. 每台 RDK 独立计算：绿灯时间 ∝ 排队车辆数 / 总车辆数
4. 保证最小绿灯时间（如 10 秒）和最大绿灯时间（如 40 秒）
5. 相位切换时：绿 → 黄(3秒) → 红，相邻相位间留有全红保护时间(2秒)
```

**丁字路口相位设计**（简化为 3 相位）：

| 相位 | 绿灯车道 | 说明 |
| ---- | -------- | ---- |
| Phase 1 | A 直行 + C 直行 | 东西对向直行（无冲突） |
| Phase 2 | A 左转 + C 右转 | A→北 与 C→北 不冲突 |
| Phase 3 | B 左转 + B 右转 | 北方双向出 |

### 3.3 特情处理

#### 救护车优先通行

```
触发条件：任意 RDK 在其负责车道检测到救护车

处理流程：
1. 若救护车所在车道当前为绿灯 → 保持绿灯直至救护车通过
2. 若救护车所在车道当前非绿灯 →
   a. 向所有节点广播 EMERGENCY 消息（MQTT QoS 2 确保送达）
   b. 所有联动车道灯黄色闪烁 3 秒
   c. 切换救护车所在车道为绿灯，其余车道红灯
   d. 救护车通过后（检测消失），恢复正常配时
```

#### 设备掉线安全降级

```
机制：心跳检测（Heartbeat）

1. 每台 RDK 每 2 秒发送心跳到 MQTT topic: traffic/heartbeat/<id>
2. 任意节点超过 6 秒未收到某节点心跳 → 判定为掉线
3. 掉线触发：所有交通灯进入黄灯闪烁模式（0.5Hz）
4. 掉线恢复：收到失联节点连续 3 次心跳后恢复正常配时
```

## 四、通讯协议选型分析

### 可选方案对比

| 方案 | 协议 | 优点 | 缺点 | 适用性 |
| ---- | ---- | ---- | ---- | ------ |
| ① ZMQ-TCP | ZeroMQ PUB/SUB | 极低延迟、无需 Broker 二进制代理 | 需自行实现 Broker、无内置 QoS | ⭐⭐⭐ |
| ② MQTT-TCP | paho-mqtt + NanoMQ | 成熟稳定、QoS 0/1/2、主题丰富 | 需部署 Broker、TCP 握手开销 | ⭐⭐⭐⭐⭐ |
| ③ MQTT-QUIC | nanomq_cli + QUIC | 更低延迟、多路复用 | 依赖 nanomq_cli 外部进程、调试复杂 | ⭐⭐⭐⭐ |
| ④ batman-adv Mesh | 无线 Ad-hoc 组网 | 无需路由器 | **不可用**——无线组网存在问题 | ❌ |

### 推荐方案：② MQTT-TCP（主用）+ 保留 QUIC 升级路径

**理由**：
1. **可靠性优先**：交通灯场景对消息到达率要求极高，MQTT QoS 2 可保证关键消息（如 EMERGENCY）严格一次送达
2. **主题模型天然匹配**：
   - `traffic/count/<direction>` — 车辆计数
   - `traffic/emergency/<direction>` — 救护车事件
   - `traffic/heartbeat/<id>` — 心跳检测
   - `traffic/phase/sync` — 相位同步
3. **有线网络满足延迟需求**：3 台 RDK 通过以太网 + 交换机直连，MQTT-TCP RTT < 1ms（实验 4 数据），完全满足交通灯秒级切换需求
4. **实验积累**：实验 4/5 已验证 NanoMQ + paho-mqtt 的完整链路

### MQTT Topic 设计

```
traffic/
├── count/<id>          # 车辆计数（QoS 0，1s 周期）
│   payload: {"lane1": 5, "lane2": 3, "ambulance_lane1": false, "ambulance_lane2": true}
├── emergency/<id>      # 紧急事件（QoS 2，仅事件触发）
│   payload: {"lane": 1, "type": "ambulance", "action": "enter"|"exit"}
├── heartbeat/<id>      # 心跳（QoS 1，2s 周期）
│   payload: {"timestamp": 1700000000.123, "status": "ok"}
└── phase/sync          # 相位同步（QoS 1，相位切换时）
    payload: {"phase": 1, "green_lanes": ["A1", "C1"], "duration": 25}
```

## 五、部署架构分析

### 方案 A：裸机直接部署（推荐 ✅）

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   RDK pi1   │     │   RDK pi2   │     │   RDK pi3   │
│  (方向 A)    │     │  (方向 B)    │     │  (方向 C)    │
│             │     │             │     │             │
│ camera.py   │     │ camera.py   │     │ camera.py   │
│ agent.py    │◄───►│ agent.py    │◄───►│ agent.py    │
│ led.py      │MQTT │ led.py      │MQTT │ led.py      │
│             │     │ + NanoMQ    │     │             │
└──────┬──────┘     └──────┬──────┘     └──────┬──────┘
       │   Ethernet Switch (有线直连)    │
       └───────────────┴────────────────┘
```

- NanoMQ Broker 运行在 pi2（或任一台 RDK）
- 所有 RDK 通过以太网交换机直连
- 每台 RDK 运行：摄像头采集进程 + 交通灯控制主进程 + LED 驱动

**优势**：最简单、延迟最低、直接访问 SPI/I2C 硬件、调试方便

### 方案 B：Docker 容器化部署

```
每台 RDK 上运行 Docker：
┌─────────────────────────────────┐
│  Docker Container               │
│  ┌───────────┐ ┌──────────────┐ │
│  │ camera    │ │ traffic_ctrl │ │
│  │ (--device │ │ (--device    │ │
│  │  /dev/    │ │  /dev/spi*)  │ │
│  │  video0)  │ │              │ │
│  └───────────┘ └──────────────┘ │
│  --privileged / --device 映射    │
└─────────────────────────────────┘
```

**可行性分析**：
- ✅ 实验 5 已验证 Docker 在 RDK X5 上可以通过 `--device /dev/i2c-5` 映射硬件设备
- ✅ 摄像头可通过 `--device /dev/video0` 映射进容器
- ✅ SPI 设备可通过 `--device /dev/spidev1.0` 映射
- ⚠️ 需要 `--privileged` 模式，存在安全隐患但在实验环境可接受
- ⚠️ 图像处理库（OpenCV）会使镜像体积显著增大

**适合场景**：需要统一环境、版本管理、方便重复部署时使用

### 方案 C：K3s + Docker 集群编排

**可行但不推荐**，原因如下：
- 本项目仅 3 台设备，每台功能固定（各管一个方向），无需动态调度
- K8s 的 anti-affinity 和自动伸缩在此场景无意义
- 引入 k3s 增加运维复杂度（证书管理、etcd、API Server），收益不大
- 若后续扩展为多路口联动场景，K3s 才有价值

### 📌 最终建议

> **开发阶段**：方案 A（裸机），快速迭代验证
> **交付展示**：方案 B（Docker），体现工程化能力，镜像一键部署
> **可选加分项**：在文档中保留方案 C 的架构设计分析，展示对容器编排的理解
